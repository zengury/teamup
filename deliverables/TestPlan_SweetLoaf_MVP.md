## 1. 测试概述

### 1.1 测试目标

本次测试的目标是验证 SweetLoaf AI 组织转型系统 MVP 版本的 **5 大核心功能模块** 是否满足 PRD 中定义的验收标准，确保系统在 **真实面包店场景** 下能够稳定、可靠、易用地运行。

### 1.2 测试范围

#### ✅ 纳入测试范围（MVP 核心功能）

| 模块编号 | 模块名称 | PRD 对应功能 | 测试重点 |
|---------|---------|-------------|---------|
| 模块1 | 语音记录经验 | F1.1 | 语音输入 → 转文字 → AI 解析 → Skill 生成 |
| 模块2 | 技能库浏览 | F1.3 | 列表展示、关键词搜索、分类筛选、技能详情 |
| 模块3 | 拍照诊断 | F2.3 | 图像上传 → AI 分析 → 诊断结果展示 |
| 模块4 | 实时操作指引 | F2.2 | 消息推送、阅读确认、收藏、基于天气/角色的个性化推送 |
| 模块5 | 员工技能地图 | F2.1 | 技能树展示、进度统计、状态更新 |

#### ❌ 不纳入测试范围（后续迭代）

| 功能 | 原因 |
|------|------|
| 流程引擎（F2.4） | MVP 中仅展示框架，未实现拖拽编排 |
| 效率看板完整版（F4.1） | 趋势图表为静态展示，数据为模拟 |
| 离线可用（F3.4） | MVP 未实现离线缓存逻辑 |
| 品质追踪完整版（F4.3） | 仅预留数据模型，未实现自动归因 |
| 跨店复制 | 后续迭代功能 |
| LINE Bot 集成 | MVP 中注册了蓝图但未实现完整交互逻辑 |
| 微信小程序 | MVP 以 Web 端为主，小程序后续迭代 |

## 2. 测试策略

### 2.1 总体策略

采用 **分层测试** 策略，从单元测试到集成测试逐层覆盖：

```
┌─────────────────────────────────────┐
│         验收测试 (UAT)               │  ← 模拟真实用户操作场景
├─────────────────────────────────────┤
│         集成测试 (Integration)        │  ← 模块间数据流转
├─────────────────────────────────────┤
│     UI 测试 (Web界面交互)            │  ← 页面渲染、按钮操作
├─────────────────────────────────────┤
│     单元测试 (Unit)                  │  ← 函数级逻辑验证
└─────────────────────────────────────┘
```

### 2.2 功能测试策略

| 测试类型 | 方法 | 覆盖内容 |
|---------|------|---------|
| **正常路径测试** | 按 PRD 验收标准逐条验证 | 核心用户旅程：创建 Skill → 搜索 → 查看 → 点赞 → 收藏 |
| **异常路径测试** | 模拟错误输入、非法操作 | 空输入、超长文本、无效ID、未登录操作 |
| **边界条件测试** | 测试数据边界 | 空数据、极大数据量、特殊字符、并发操作 |

### 2.3 语音测试策略（模块1专项）

由于 MVP 使用 **模拟模式（Mock Mode）**，语音测试策略如下：

| 测试维度 | 方法 | 模拟数据来源 |
|---------|------|-------------|
| 普通话语音识别 | 使用模拟文件名触发预设文本 | `voice_processor.py` 中的 `mock_transcripts` 字典 |
| 闽南语识别 | 测试闽南语词汇映射函数 | `translate_taiwanese()` 函数 |
| 闽南语+普通话混合 | 测试混合文本解析 | 预设混合文本如"今仔日天气较冷，面温爱拍到26度" |
| 语音→Skill 转换 | 测试 `create_skill_from_voice()` 完整流程 | 从语音文本到数据库存储的全链路 |

> **生产环境注意事项**：正式上线时需使用真实 Whisper API 或 Google STT 服务，建议在上线前安排 **真实语音录制测试**，用 10 段以上真实员工语音（含闽南语）验证识别准确率。

### 2.4 图像测试策略（模块3专项）

同样使用 **模拟模式**，图像测试策略如下：

| 测试维度 | 方法 | 模拟数据来源 |
|---------|------|-------------|
| 正常品相诊断 | 文件名含 "perfect" 关键词 | `vision_processor.py` 中的 `mock_diagnoses` 字典 |
| 烤焦品相诊断 | 文件名含 "burnt" 关键词 | 同上 |
| 烘烤不足诊断 | 文件名含 "under" 关键词 | 同上 |
| 底部偏深诊断 | 文件名含 "dark" 关键词 | 同上 |
| 未知文件诊断 | 文件名无匹配关键词 | 返回默认诊断结果 |

> **生产环境注意事项**：正式上线时需使用 OpenCV 真实颜色分析。建议收集 **50 张以上真实面包照片**（含不同光线条件）来校准颜色阈值。

### 2.5 易用性测试策略（全模块覆盖）

由于 SweetLoaf 员工多为非技术人员，易用性是核心关注点：

| 测试维度 | 方法 | 通过标准 |
|---------|------|---------|
| **3步原则** | 统计每个功能的操作步骤数 | 任何功能 ≤ 3 步 |
| **语音优先** | 验证核心操作是否支持语音 | 创建 Skill、查询 Skill 支持语音 |
| **零培训上手** | 模拟新员工首次使用 | 3 分钟内完成第一次 Skill 创建 |
| **反馈及时性** | 测量操作后的反馈时间 | 语音识别 ≤ 2 秒，拍照诊断 ≤ 5 秒 |
| **错误提示友好性** | 检查错误提示文案 | 使用员工能理解的语言，不出现技术术语 |
| **移动端适配** | 在手机屏幕尺寸下测试 | 所有页面在 375px 宽度下正常显示 |

### 2.6 安全测试策略

| 测试维度 | 方法 | 预期结果 |
|---------|------|---------|
| **未登录访问** | 直接访问需要登录的页面 | 重定向到登录页 |
| **跨用户操作** | 用户 A 尝试操作用户 B 的数据 | 应被权限控制拦截 |
| **XSS 防护** | 在输入框中输入 `<script>` 标签 | 标签被转义，不执行 |
| **SQL 注入** | 在搜索框中输入 `' OR 1=1--` | 不泄露额外数据 |

## 6. 风险与缓解措施

| 风险 | 影响 | 概率 | 缓解措施 |
|------|------|------|---------|
| **模拟模式与真实模式差异** | 模拟模式下测试通过的逻辑，真实 API 调用时可能失败 | 高 | 在测试计划中明确标注模拟模式限制；上线前安排真实 API 集成测试 |
| **闽南语识别准确率不足** | 员工使用闽南语时语音识别效果差，导致体验下降 | 中 | 提前收集闽南语测试样本；在测试用例中增加闽南语专项测试 |
| **图像诊断准确率不足** | 不同光线条件下拍照，颜色分析偏差大 | 中 | 测试用例覆盖不同光线场景；建议收集真实面包照片校准阈值 |
| **移动端兼容性问题** | 部分员工使用老旧手机，页面显示异常 | 中 | 测试覆盖 iOS 12+ / Android 8+；使用响应式设计 |
| **并发使用性能问题** | 12 人同时使用时系统响应变慢 | 低 | 单元测试中模拟并发创建；上线前进行压测 |
| **员工抵触使用** | 非技术员工觉得系统难用，拒绝使用 | 低 | 易用性测试严格把关；确保 3 步原则落实 |

## 7. 验收标准

### 7.1 测试通过标准

| 指标 | 标准 |
|------|------|
| 测试用例通过率 | ≥ 95%（P0 用例 100% 通过） |
| 严重缺陷数 | 0 个 |
| 一般缺陷数 | ≤ 5 个（上线前修复） |
| 测试覆盖率 | 核心功能代码覆盖率 ≥ 80% |

### 7.2 缺陷等级定义

| 等级 | 定义 | 处理要求 |
|------|------|---------|
| **P0-致命** | 核心功能不可用，数据丢失，系统崩溃 | 立即修复，阻塞发布 |
| **P1-严重** | 功能不符合 PRD 要求，无替代方案 | 发布前必须修复 |
| **P2-一般** | 功能可用但体验不佳，有替代方案 | 可在下一迭代修复 |
| **P3-建议** | 体验优化建议，不影响功能使用 | 记录到产品 backlog |
